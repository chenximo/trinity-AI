本文把「刊例治理 / 账单核对 / 销售定价」收成**一套运营系统**的设计，供继续评审。不替代各子域已有 SOP；冲突时以各子域工程真源为准，本文记录产品级约定。

**框架完备性（2026-07-31）**：三柱作为运营主框架**已可定稿**；另需横切能力（map 缺口、告警、例外登记、审计、汇率口径），不升第四柱。后台上市状态维持「上架/下架」，价审用独立「价格校验」字段（见 §4.2）。

## 1. 目标与边界

### 1.1 要解决什么

1. 工程师把模型接到后台后，如何**安全地**完成基础刊例校验与写回。  
2. 如何定期发现「官方锚 vs 进货渠道 vs 线上刊例」的偏差，并告警到人。  
3. 如何按月核对「平台成本/用量 vs 上游实付/用量」，确认后再回填实付。  
4. 如何与**对客销售定价**衔接且不混真源。

### 1.2 明确不做什么

| 不做 | 说明 |
|------|------|
| AI/流水线静默改生产刊例或实付 | 必须人确认（或明确授权的写 API） |
| 用转售渠道价反推「官方价」 | 官方锚只来自原厂文档/seed |
| 缺缓存等字段用比例推算 | 表无则 ⚠ |
| 账单对账与挂牌巡检混成一次任务 | 分柱、分触发、分报告 |

### 1.3 名称

| 对外/对内称呼 | 含义 |
|---------------|------|
| **模型供应与定价运营** | 本系统总称（推荐） |
| 价格系统 | 口语可保留，文档优先用总称 |
| 刊例治理 / 账单核对 / 销售定价 | 三柱子名 |

行业近义：Catalog lifecycle + Pricing governance + Human-in-the-loop Ops；关键变更采用 Maker–Checker（经办出简报、产品确认）。

## 3. 人机分层（HITL）

| 层级 | 机器（流水线 / Skill / 门禁） | 人 |
|------|------------------------------|-----|
| 检测 | 抓价、对表、算差%、gate、钉钉告警 | — |
| 建议 | 建议刊例、归因提示、应回填实付数字 | — |
| 决策 | — | 战略价、折扣、是否上架、是否认账单差 |
| 写库 | 仅在「确认」动作后调 API（规划） | 确认按钮 / 手填实付 |
| 例外 | 读取 annotations，不再 blocking | 登记例外 |

**原则**：机器负责发现与汇总；人负责定价与放行。

### 3.1 产品 vs 运营（谁做什么）

| | 产品经理 | 运营（可兼任） |
|--|----------|----------------|
| 职责 | 定流程、字段、门禁、优先级、验收 | 按 SOP 执行：价审确认、填账单、跟告警 |
| 本系统文档 | **产品产出**（运营系统设计） | 使用方 |
| 日常点确认 / 回填实付 | 可兼；流程稳后宜交运营 | **主责执行** |

小团队常一人兼两边：设计迭代归产品视角，每周执行归运营视角。

## 4. 柱① — 刊例治理（官方基础刊例）

### 4.1 业务故事（不含商务谈判细节）

```text
工程师对接模型 → 后台「下架」+「价格校验=未校验」（可内测、不对客）
       ↓
触发价审（人点按钮 / 对 AI 下口令；后期可半自动）
       ↓
价格流水线跑校验（官方 + AIGC/TokenHub 等 + 线上）
       ↓
生成「本次修改简报」+ 建议刊例（价审任务态：进行中/完成/驳回）
       ↓
产品核对简报 → 确认更新刊例 →「价格校验=已校验」
       ↓
点「上架」（门禁：须已校验；超管强上须审计）
```

存量漂移：走既有 **每周 `pricing:inspect`**，不替代上新主路径。

### 4.2 后台状态：上架/下架 + 价格校验（已拍板）

后台**主状态只保留**：

| 上市状态 | 含义 |
|----------|------|
| **上架** | 对客可卖、进路由 |
| **下架** | 不对客（新建未开、临时关、价未就绪） |

**最有必要新增的字段**（二值即可）：

| 字段 | 取值 | 谁改 |
|------|------|------|
| **价格校验** | `未校验` / `已校验` | 价审确认写回刊例后 → `已校验`；大改价/换主线路 → 打回 `未校验` |

可选 P1：`最近价审简报 ID`、`校验时间`。

**不**把「价审中 / 价审通过 / 驳回」做成模型主状态；它们属于**价审任务/简报**：

| 口头说法 | 后台落点 |
|----------|----------|
| 待上架 | `下架` + `未校验` |
| 价审中 | 价审任务进行中；模型仍为 `下架` + `未校验` |
| 价审通过 | `已校验`（通常仍先下架，再点上架） |
| 已上架 | `上架` + `已校验` |
| 驳回 | 任务失败原因；模型保持 `下架` + `未校验` |

#### 门禁逻辑

```text
允许「上架」⟺ 价格校验 = 已校验
              （例外：超管强上 + 强制写审计原因）

下架：随时可下；默认保留「已校验」（再上架仍要求已校验）

触发打回未校验（建议）：
  - 主供应线路变更
  - 刊例入/出/缓/缓存写任一项人工大改且未经价审
  - 产品/运营手动「要求重审」
```

#### 双重核验

常规：**产品确认简报即可**，不要求开发再点「价审」。  
高风险（新供应商/新模态/差价超阈/计量字段变）：可选工程做**配置复核**（路由、单位、缓存字段、试调），不审卖价。

### 4.3 触发方式

| 方式 | 适用 | 优先级 |
|------|------|--------|
| **人工「发起价审」** / 对 AI「校验某某刊例」 | 上新、单点改价 | **P0 默认** |
| **定时巡检** `pricing:inspect` | 全量漂移 | **P0 已有** |
| **半自动**（新模型 `下架+未校验` 且线路就绪） | 降摩擦 | P2；须幂等与防刷 |

**禁止**：校验通过后无确认自动改生产刊例。

### 4.4 价审简报（一等公民）

每次价审至少包含：

| 字段 | 说明 |
|------|------|
| 任务 ID / 时间 / 操作者 | 审计 |
| 模型列表 | Trinity ID |
| 旧刊例 → 建议刊例 | 入/出/缓等 |
| 依据 | 官方锚、主上游、差% |
| map 状态 | 已映射 / 缺 map / 仅刊例 |
| 结论 | 可确认写回 / 须补锚 / 须登记例外 |
| 风险标记 | 差价超阈、新模态、计量字段变更 |

落盘建议：`pricing/output/ops/listing-briefs/YYYYMMDD-<id>.md`（或控制台任务表）。

### 4.5 写回运营后台

| 阶段 | 做法 |
|------|------|
| P0 | 简报 + 建议 JSON → 产品/工程在后台手改刊例 |
| P1 | 控制台「确认更新」→ 调管理端写价 API（鉴权、审计、幂等） |
| API 能力（规划） | 读：模型与当前价；写：批量更新 user/cost/official 单价 + briefId |

### 4.6 查看与 Excel

| 场景 | 设计 |
|------|------|
| 日常查看 | 控制台：模型维度看刊例 / 官方 / 主上游 / 差% / 状态 |
| 商务全量对照 | 既有 `trinity-pricing-*.xlsx` 下载；可选只读预览 |
| Excel 上传 | **非主路径**；仅例外批注/商务导入，不替代 suppliers + `/v1/prices` 真源 |

### 4.7 供应商 vs 官方偏差告警

| 步骤 | 执行方 |
|------|--------|
| 检测（listing-compare / gate / 钉钉） | 机器 |
| @产品 + 开发 | 告警机器人（已有 webhook 约定） |
| 调线路折扣、战略价、是否跟价 | **人**（产品+开发协作） |
| 登记例外免反复告警 | 人写 `pricing-annotations` 等 |

供应商线路**手动录入** = 配置真源（人）；机器只做交叉与告警。

### 4.8 与现有工程映射

| 设计步骤 | 现有能力 |
|----------|----------|
| 刷官方/上游 | `pricing:refresh` / 各 `pricing:supplier:*` |
| 交叉与门禁 | `pricing:gate` · `validate:compare` |
| 每周巡检 | `pricing:inspect` · [operations.md](../../apps/trinity-product/docs/ai-api-platform/pricing-sources/operations.md) |
| 上新模型 | [add-model-sop](../../apps/trinity-product/docs/ai-api-platform/pricing-sources/add-model-sop.md) |
| 刊例发布 | [listing-deploy](../../apps/trinity-product/docs/ai-api-platform/pricing-sources/listing-deploy.md) |
| Skill | `trinity-official-pricing` |

**待补强（相对本文）**：map 缺口显式清单；人话「价审简报」模板；后台 **价格校验** 字段与写价 API；上架门禁（未校验不可上）。

## 5. 柱② — 账单核对

### 5.1 业务故事

```text
后台月度对账（系统）：账单月、起止、上游、平台成本 USD、平台 Token
       ↓
人从上游控制台拉：实付 CNY/USD、上游 Token（及附件名）
       ↓
触发核对（按钮 / 交给 AI · 同一 SOP）
       ↓
生成核对报告（金额差、量差、是否预期内、应回填数字）
       ↓
人确认 → 手动回填管理后台「上游实付」
```

### 5.2 对账口径（冻结）

| 项 | 约定 |
|----|------|
| 对账汇率 | 默认 **CNY ÷ 6.5 → USD**（与成本单价÷6.5 同口径） |
| 平台 Token | 入+出+缓（导出列规划中） |
| 左右 | 上游=供应商账单；平台=Trinity 成本；¥ 只标上游 |
| 写后台实付 | **仅确认报告后由人填写**；Skill 默认不写库 |

### 5.3 L0 阈值（默认，可调）

| 档 | 条件 | 动作 |
|----|------|------|
| 预期内 | \|金额差\|≤5% 且（无 Token 或 \|量差\|≤5%），或 \|Δ$|≤10 | 可建议回填 |
| 关注 | 金额差 5%～15% | 报告标明；回填须确认 |
| 下钻 | \|差\|>15% 或 \|Δ$|>50 或倍数≥2× | 进入排查 SOP |

### 5.4 差大时排查 SOP（轻量）

```text
1) 对齐账单窗口（起止是否一致）
2) 量差为主 → 测试未入账 / Token 口径 / 漏计
3) 量齐钱不齐 → 转回柱① 查成本单价/刊例
4) 仍不清（如腾讯 L2）→ 标准日结 vs 月桶；禁止跨日均摊下结论
5) 结论写入 notes / recon-report；再决定是否回填实付
```

### 5.5 触发：API vs AI

| 阶段 | 建议 |
|------|------|
| P0 | 导出/粘贴平台侧 + 人工上游三数 → Skill 出报告 |
| P1 | 控制台拉平台月度 API → 表单填上游 → 一键出报告 |
| 分析逻辑 | **同一套**（勿 API 一套、聊天一套） |

### 5.6 与现有工程映射

| 设计 | 现有 |
|------|------|
| 目录 | `pricing/billing-reconciliation/` |
| Skill | `trinity-billing-reconciliation`（报告先行、实付后填） |
| 后台 | 月度按上游导出；规划加平台 Token、统计起止 |

## 6. 柱③ — 销售定价（对客）

### 6.1 定位

在**已发布的基础刊例 / 成本锚**之上，做销售折、档位、套餐、充值与运行时扣费。

真源与流程见产品手册 **商用计费与充值**；本运营系统只要求：

- 柱① 变更基础刊例后，③ 须有检查点（销售折是否仍满足 GM 护栏）。  
- ③ 不改官方 seed，不改账单实付。

### 6.2 与①②的接口

```text
① 基础刊例/成本价 ──► ③ 销售折与对客价
② 实际进货成本（月度）──► 财务/毛利复盘（可反馈③策略，不自动改折）
```

## 7. 共享约定

### 7.1 汇率三口径（禁止混用）

| 口径 | 用途 |
|------|------|
| **价目 ÷6.5** | 人民币挂牌写入 cost/对比官方 |
| **账单对账 6.5** | 上游现金 CNY → USD vs 平台成本 USD |
| **充值/付汇市价** | 客户充值与购汇；仅现金损益附录 |

### 7.2 三层挂牌价（柱①内）

| 层 | 含义 |
|----|------|
| 官方价 | 厂商文档锚 |
| 进货/转售挂牌 | AIGC、TokenHub、百炼等 |
| 线上刊例 | Trinity `/v1/prices` 对客基础价 |

中转站-cust 等「原厂直连拷贝」= 官方价复制，不是独立官网爬取。

### 7.3 角色（RACI 简表）

| 活动 | 工程 | 产品 | 运营（可兼） | 商务 |
|------|------|------|--------------|------|
| 模型接入（下架+未校验） | **R** | C | I | C |
| 发起价审 / 确认刊例简报 | C | **R**（定规则） | **R**（日常执行） | I |
| 点上架（须已校验） | C | C | **R** | I |
| 供应商折扣与战略例外 | C | **R** | C | **C/R** |
| 配置复核（高风险） | **R** | C | I | I |
| 账单报告确认与回填实付 | I | C（规则） | **R** | C |
| 销售折策略 | C | **R** | C | C |
| 本运营系统设计/迭代 | C | **R** | C | I |

R=执行 · C=协商 · I=知会

## 9. 分期实现路线

### P0 — 流程跑通（少改后台）

- ①：人工/AI 触发现有 refresh·gate·compare → **价审简报模板**落地；确认后手改后台刊例；钉钉告警保持。  
- ①：巡检 SOP 增加 **map 缺口 + 本轮纪要** 说明。  
- ②：平台导出（规划 Token 列）+ 人工上游三数 → Skill 报告 → 手填实付。  
- ③：沿用现有。  

### P1 — 控制台闭环

- ①：后台加 **价格校验** + 上架门禁；「发起价审」+ 简报页 + **确认写价 API**。  
- ②：月度 API 出平台成本/Token；报告归档。  
- 告警列表可在控制台打开 brief。  

### P2 — 降摩擦

- ①：新模型进入「下架+未校验」后可半自动排队价审（仍要人确认写回）。  
- ②：超阈值一键创建下钻任务（日结/分模型）。  
- ①↔③：刊例变更触发销售折 GM 检查。

## 10. 开放问题（继续讨论）

### 已拍板

| # | 结论 |
