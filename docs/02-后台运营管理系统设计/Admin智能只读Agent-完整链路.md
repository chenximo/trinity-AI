# Admin 智能只读 Agent · 完整链路

> **日期**：2026-08-25  
> **依据**：V4.2 设计稿《Admin 智能只读 Agent 助手设计》《Admin 智能只读 Agent 实现详细设计》（2026-08-17 已上线）  
> **本文作用**：把一次提问从入口走到答案的全流程，以及选型、分工、优缺点、产品经理交付清单收成一篇可独立阅读的说明；不替代上述两份设计真源。

---

## 0. 一句话

运营在 Admin 用中文问业务数据。系统走 **受控 Agent Loop**（最多 4 轮）：**模型只负责点菜单（选 Tool、填参数）和把结果写成中文**；查库、回填、鉴权全在服务端。折扣、TPM、余额等硬事实一律由白名单 Tool 查只读库。不能闲聊、不能改数、看不到任何 Key。

没有单独的「意图识别」服务。对外 HTTP 只有提问口 `POST /v1/admin/ops-agent/ask`；Tool 不是让模型去打的一堆 API 地址。

---

## 1. 属于哪种助手

选型决策树：

```
问题是否跨多个数据源？
 ├─ 否 → 问题模式是否固定、答案在单一知识库？
 │ ├─ 是 → 传统 RAG
 │ └─ 否（问题模糊、需推理）→ Single-Agent RAG
 └─ 是 → 是否需要不同专业视角分别检索再汇总？
    ├─ 是 → Multi-Agent RAG
    └─ 否 → Single-Agent RAG（带多工具调用）  ← 本助手
```

| 判定 | 结论 |
|------|------|
| 是否跨多个数据源 | **是**：KB + 用户/折扣/TPM/模型线路/钱包等不同 Tool 与表 |
| 是否多专家分别检索再汇总 | **否**：只有一个 Orchestrator、一个模型、一份 Tool 白名单 |
| 落点 | **Single-Agent RAG（带多工具调用）** |
| 更精确的工程叫法 | 单 Agent + 轻量检索增强 + 白名单 Tool 循环（ReAct） |

不是传统 RAG：答案在活库里，不在一份 FAQ。KB 只教「去哪查、怎么查」。  
不是 Multi-Agent：没有折扣专家 / TPM 专家并行检索再合成。  
MVP 不做向量库，KB 是 Markdown + 关键词 / BM25。

---

## 2. 是不是 Agent Loop

**是。** `ask` 的核心是 ReAct 循环：想 → 调工具 → 看结果 → 再想，上限 4 轮。

```
for round in 1..maxToolRounds(4):
    调模型
    若还有 tool_call → 服务端执行 Tool → 结果写回 messages → continue
    若已是最终答案 → break
```

鉴权、KB 检索、裁剪 Tool schema、出口打码、审计、计费在循环外，包着这个 Loop。

---

## 3. 答案是不是模型推算的

**不是。** 数字和事实来自 Tool 查只读库；模型不负责把折扣「算出来」。

| 谁 | 干什么 |
|----|--------|
| 模型 | 选 Tool、填参数、把 Tool JSON 说成人话；解释「0.7 = 七折」 |
| 服务端 Tool | 用 RO 账号查白名单表 / 既有查询，返回结构化数据 |
| 服务端拼表 | 价目等长表由 `OpsAgentStructuredAnswerComposer` 拼 Markdown，不依赖模型写长文 |
| 护栏 | 闲聊拒绝、无权限 forbidden、出口打码 |

设计约束：答案必须能落到工具结果，否则明确说「知识库未覆盖」。evidence 记录真实 Tool 名、入参、行数。

---

## 4. 分工：选工具、查数、回填分别是谁做的

**只有「选 Tool、填参数」和「写成中文」是大模型。查数和回填是服务端。**

```
模型：输出 {"tool":"lookup_user","args":{"email":"foo@x.com"}}
        ↓
服务端：校验权限 / 入参 → RO 查库 → 拿到 {userId:123}
        ↓
服务端：把这段 JSON 写进 messages（回填）
        ↓
再调模型：模型看到结果，决定下一轮 Tool 或出最终答案
```

| 步骤 | 谁做 | 模型是否经手 |
|------|------|----------------|
| 选 Tool、填参数 | **大模型** | 自己产出一张「订单」 |
| 执行查询（RO / 既有接口） | **服务端 Orchestrator** | 模型不连库；`run_readonly_sql` 也是服务端在护栏下执行 |
| 把结果写回对话 | **服务端** | 模型下一轮才能读到 |
| 写成中文答案 | **大模型**（长表可服务端拼） | 基于回填后的 Tool 结果 |

大模型碰不到数据库账号，也执行不了 Tool。它只输出「要调谁、参数是什么」。这正是只读助手安全边界能成立的原因。

---

## 5. 提问有没有做意图识别

**没有做成「先分类意图再走流程」那一套。** 没有 `intent=查折扣 / 查TPM` 的分类器，也没有槽位填充引擎。

和「意图」沾边的只有两层浅处理，都在进 Loop 之前：

| 步骤 | 是不是意图识别 | 实际在干什么 |
|------|----------------|--------------|
| 闲聊启发式 | 否，规则关键词 | 明显闲聊可短路径 `refused`，仍可再交给模型判断 |
| KB 关键词 / BM25 | 否，检索 | 把相关说明书塞进 prompt，不是打意图标签 |
| 按权限裁剪 Tool | 否，鉴权 | 没权限的 Tool 根本不给模型看 |

**「这个问题要干什么」是模型在 Loop 里用选 Tool 隐式完成的。**  
问折扣 → 它自己决定 `lookup_user` 再 `get_user_discount`。选错或漏选，就是路由失败，没有上游意图分类来兜底。

| | 传统客服机器人 | 本助手 |
|--|----------------|--------|
| 怎么理解问题 | 先分类：这是「查折扣」；再抽槽：邮箱 = foo@x.com | 不先分类；把菜单给模型，当场决定点哪几个、按什么顺序 |
| 好处 | 话术少时正确率高、路径死 | 一句里可以又查折扣又查 TPM，不必为每种问法写死一条意图 |
| 坏处 | 新问法要加意图 | 菜单点错、漏点、参数填错都可能发生，所以要白名单、权限、轮次上限 |

## 6. 「选 Tool、填参数」直白解释

把模型当成一个**只会点菜单、不会进后厨**的服务员。

服务端先给它一份**菜单**（Tool schema），每个菜是一个已经写好的查询函数：

| 菜单项（Tool） | 要点什么（参数） |
|----------------|------------------|
| 按邮箱找用户 `lookup_user` | `email` |
| 查折扣 `get_user_discount` | `userId` |
| 查 TPM `get_user_rate_limit` | `userId` |

运营说：「查一下 foo@x.com 的折扣。」

模型**不会去查库**。它只做两件事：

1. **选 Tool** = 判断该用哪个现成查询（先找人，再查折扣）
2. **填参数** = 把「查谁、查哪个模型」填进那个查询的空格（邮箱 `foo@x.com`；查到 `userId=123` 后再填进折扣查询）

相当于只输出一张订单：

```text
请后厨做：lookup_user
参数：email = foo@x.com
```

后厨（服务端）按订单去做、把结果端回来。模型再看结果，决定下一张订单，或开始用中文汇报。

---

## 7. Tool 是不是 API 接口

**对模型来说像接口契约，但不是它去调的 HTTP API。**

Tool 是 Admin 服务端里**写死的查询函数**（Java `OpsAgentTool`），挂在白名单注册表上。模型只输出「名字 + 参数」，真正执行的是 `trinityai-admin` 进程内部。

| | 是不是 |
|--|--|
| 给模型用的函数签名（名字、参数、返回什么） | 是 |
| 浏览器 / 模型直接打的 HTTP API | **不是** |
| 和 Admin 页面那套对外 REST 是同一条 URL | **不是** |

对运营暴露的 HTTP 只有提问口：`POST /v1/admin/ops-agent/ask`。后面 20 多个 Tool 都是这个接口**内部**的函数，不单独对外开放。

和现有 Admin API 的关系：查的是同一类业务数据，**不是**模型去调页面那个 GET。

```text
运营以前：打开用户页 → 调 GET /admin/users/{id}/discount
现在助手：模型点 get_user_discount → 服务端用 RO 查同一类表 → 把 JSON 回给模型
```

知识库 `20-admin-apis.md` 只是告诉模型「页面上那个查询，对应哪个 Tool」。  
Function Calling 里的 tool，本质就是：**给模型看的函数签名 + 程序里真正执行的那段代码**。可以包一次 SQL、包一个内部 Service，对模型长得都一样。

## 8. 业界是不是一般都这么设计

**是。** 现在主流 Agent / 带工具的 Chat，核心就是这一套，名字可能不同：

| 常见叫法 | 含义 |
|----------|------|
| Function Calling / Tool Use | 模型输出「调用哪个函数 + JSON 参数」，程序去执行 |
| ReAct（Reason + Act） | 想一步 → 调工具 → 看结果 → 再想 |
| Agent Loop | 上面这件事循环做，直到能回答 |

OpenAI、Anthropic、Gemini 的「给模型 tools、模型返回 `tool_calls`」就是这个。查数助手、IDE 助手多数也是：**菜单由系统定死，点菜和填表交给模型，干活交给代码。**

业界常见三档，本助手选中间档：

| 做法 | 谁决定查什么 | 典型场景 |
|------|----------------|----------|
| 意图分类 + 固定接口 | 规则 / 小分类模型 | 话术少、流程死（「查话费」「改密码」） |
| **Function Calling + Tool 白名单** ← 本助手 | 大模型选工具、填参数 | 问法活、查询种类多、但不能乱来 |
| 模型自由写 SQL / 多 Agent 自己规划 | 模型自由度最高 | 内部分析、研究向；安全和成本更难控 |

查运营数据、要安全、问法又不固定，业界默认就是 **白名单 Tool + Function Calling**，很少再单独做一层重意图识别——除非话术极少、正确率必须接近 100%。

本助手还多了两处业界也常见的收口：最多 4 轮，避免点菜没完；工具结果必须能对上答案，避免模型空口报数。

## 9. 全链路总图

```
运营提问（Fab / /ops/agent）
    │  Admin JWT + admin.ops.agent.use
    ▼
进门：鉴权 → 限流 → 校验字数 → 建/载会话 → 闲聊启发式
    ▼
装弹药：KB 检索 Top-K + 固定注入 overview/security
        按权限裁剪 Tool schema
    ▼
┌─ Agent Loop ≤ 4 轮 ──────────────────────────────────┐
│  模型：选 Tool、填参数（点菜单、填订单）                │
│  服务端：执行查询（RO 查库）→ 把结果回填进 messages     │
│  直到模型输出 final，或轮次用尽                         │
└──────────────────────────────────────────────────────┘
    ▼
出门：出口打码 → 写审计表（主库）→ 返回 Markdown + evidence
    │
    └── 各轮 LLM 走正式 /v1/chat/completions，系统用户 gift 计费
```

## 10. Case：查用户折扣（走完全流程）

**问法**：`查一下用户 foo@x.com 的模型折扣列表，并说明折扣含义`

**前置**：运营小王已登录 Admin，同时有 `admin.ops.agent.use` 与 `admin.users.list.view`。

### 10.1 前端

- 入口：全局浮层（气泡弹层）或页 `/ops/agent`
- `POST /v1/admin/ops-agent/ask`

```json
{
  "sessionId": null,
  "question": "查一下用户 foo@x.com 的模型折扣列表，并说明折扣含义"
}
```

- Header 带 Admin JWT；发送后禁用输入，展示「查数中」；最长等 120 秒。

### 10.2 进门（循环外）

| 步 | 做什么 | 本案结果 |
|----|--------|----------|
| 鉴权 | JWT + `admin.ops.agent.use` | 通过 |
| 限流 | Redis：日配额 / 并发 | 未超 |
| 校验 | 非空、≤500 字 | 通过 |
| 会话 | `sessionId=null` → 新建 | `oas_9f3a…` |
| 闲聊启发式 | 是否明显闲聊 | 否，继续 |

无权限则此处 403，不调模型。RO 未配则 503，不进 Loop。

### 10.3 装弹药（循环外）

**KB（轻量 RAG）**

- 固定注入：`00-overview.md`、`90-security.md`
- 按问题关键词再抽 Top-K，本案会命中：
  - `10-tables.md`：折扣在 `app_user_model_discount`
  - `30-tools.md`：先 `lookup_user` 再 `get_user_discount`；系列折用 `expand_user_discount`
  - `40-faq-examples.md`：标准问法

**裁剪 Tool schema**

- 有 `admin.users.list.view` → 模型能看到 `lookup_user`、`get_user_discount`、`expand_user_discount`、`search_kb` 等
- 无对应细权的 Tool 不下发（或调用时 `FORBIDDEN`，不查库）
- 不存在读取 `user_api_key` / 上游 Key 的 Tool

拼好 messages：`[system+KB, user问题]`。

### 10.4 Agent Loop

数字全部来自 RO 库。现网默认 **JSON 协议**（native tools 不稳则降级）。

```
Round 1  模型点菜单：lookup_user(email)
         服务端 RO 查 app_user → userId=123（回填）
Round 2  模型点菜单：get_user_discount(userId=123)
         服务端 RO 查 app_user_model_discount
         → flash 0.70，DeepSeek 系列 0.80（回填）
Round 3  模型点菜单：expand_user_discount(userId=123)
         服务端把系列 0.80 展开成模型明细（回填）
Round 4  模型出 final 答案（不再点菜单）
```

#### Round 1 — 找人

模型输出：

```json
{"tool":"lookup_user","args":{"email":"foo@x.com"}}
```

服务端：校验邮箱格式 → 二次鉴权 `admin.users.list.view` → `xh_admin_ops_agent_ro` 查只读副本 → 过滤系统账号 → 回填 `{ userId:123, email:"foo@x.com" }`。

`123` 是查出来的，不是模型猜的。

#### Round 2 — 查折扣

```json
{"tool":"get_user_discount","args":{"userId":123}}
```

RO 返回：

```json
{
  "models": { "deepseek-v4-flash": 0.70 },
  "families": { "12": 0.80 }
}
```

`0.70` / `0.80` 来自 `app_user_model_discount`。

#### Round 3 — 展开系列

问题要求「说明含义」，系列折需展开，再调 `expand_user_discount`。  
不展开时，运营会误以为只有 flash 有折。

#### Round 4 — 收口

```json
{
  "final": true,
  "refused": false,
  "answer_markdown": "用户 **foo@x.com**（id=123）配置了以下折扣：\n- `deepseek-v4-flash`：0.70（七折）\n- 系列 DeepSeek：0.80（八折，展开后该系列模型均生效）\n\n未单独配置的模型按官方价（系数 1.0）。"
}
```

模型只做表述。若写成 0.5 而 evidence 是 0.7，验收失败。  
价目类长表走服务端拼表；本案列表短，走模型成文即可。

### 10.5 出门（循环外）

1. **打码**：扫答案 / evidence 中的 `xh-` / `sk-` / `Bearer`
2. **落库（主库，不是 RO）**
   - `admin_ops_agent_turn`：问题、答案、evidence、耗时
   - `admin_ops_agent_tool_call`：三轮 Tool 名、入参、ok、耗时
3. **计费**：各轮 LLM 走 `POST /v1/chat/completions`，`model=deepseek-v4-flash`，系统用户（正式 `user_id=191`）扣 gift，写 `usage_event`
4. **返回前端**

```json
{
  "sessionId": "oas_9f3a…",
  "answerMarkdown": "用户 **foo@x.com**（id=123）…",
  "evidence": [
    { "tool": "lookup_user", "args": { "email": "foo@x.com" }, "rowCount": 1 },
    {
      "tool": "get_user_discount",
      "args": { "userId": 123 },
      "rowCount": 1,
      "preview": { "models": { "deepseek-v4-flash": 0.7 }, "families": { "12": 0.8 } }
    },
    { "tool": "expand_user_discount", "args": { "userId": 123 }, "rowCount": 8 }
  ],
  "model": "deepseek-v4-flash",
  "platformRequestId": "req_…",
  "latencyMs": 1820,
  "refused": false
}
```

气泡展示 Markdown；证据区可展开，看到查了哪些 Tool。

### 10.6 同会话追问

再问「他 TPM 上限呢？」带同一个 `sessionId`。  
最近 K 轮进 messages（已有 userId=123），新 Loop 可能直接 `get_user_rate_limit`。  
该 Tool 需要 `admin.users.user_tpm_monitor.view`；没有则 `tool_forbidden`，不查库。

## 11. 中途退出

| 情况 | 停在哪 | 结果 |
|------|--------|------|
| 没 `ops.agent.use` | 进门 | 403，无 Loop |
| 未配 RO | 进门后 | 503「数据源未就绪」 |
| 「今天天气怎么样」 | 启发式或模型拒绝 | `refused=true`，零业务 Tool |
| 「把他的 API Key 给我」 | 提示词 + 无密钥 Tool + 打码 | 拒绝，不碰 `user_api_key` |
| 无 `users.list.view` 问折扣 | Round 内 Tool | `{error:FORBIDDEN}`，不查库 |
| 4 轮还没收口 | 循环上限 | 带已有 evidence 的友好错误 |

## 12. 谁对答案负责

| 内容 | 谁产出 |
|------|--------|
| userId=123、系数 0.70 / 0.80 | Tool + RO 库（服务端执行） |
| 「该查折扣还是 TPM」、参数填什么 | 模型点菜单 |
| 「七折」「未配置则官方价」 | 模型按 KB 表述 |
| 查了哪些表 / 接口 | evidence（服务端记录） |
| 花了多少 Token | 正式 chat 计费链路 |

## 13. 过程清单（对应一次 ask）

1. **门控**：Admin JWT、`admin.ops.agent.use`、日配额 / 并发
2. **检索增强（轻量 RAG）**：关键词 / BM25 抽 KB，不是向量库；**不是意图分类**
3. **规划 / 点菜单**：一个 LLM 选白名单 Tool、填参数
4. **执行**：服务端 P0 全走 Agent RO；每个 Tool 再校验细权
5. **回填再规划**：服务端把 Tool 结果塞回 messages，最多 4 轮
6. **生成**：自然语言答案 + evidence；长表可服务端拼
7. **护栏**：拒绝闲聊 / 改数 / 要 Key；出口脱敏
8. **记忆（弱）**：同 session 短多轮，不是长期记忆
9. **审计与计费**：会话 / 轮次 / Tool 落主库；系统用户正常扣 gift

没有的过程：独立意图识别、多 Agent 分工、向量召回、重排序、写操作、外网搜索、自动补给额度、模型直连 HTTP API。

## 14. 优缺点

相对「传统 RAG、Multi-Agent、运营自己点页面 / 写 SQL」。

### 优点

1. **和问题匹配**：折扣、TPM、钱包在活库里，传统 RAG 只会复述文档；跨表又不需要多个专家 Agent。
2. **安全边界清楚**：只读 RO、Tool 白名单、细权二次校验、密钥整表拒绝、出口打码、禁闲聊。模型没有「自由写 SQL / 改库」的主路径。
3. **数字可核对**：系数来自 Tool，evidence 能对上 Admin 页面。
4. **比 Multi-Agent 简单**：一个编排器，排障就是看 4 轮调了哪个 Tool。
5. **成本与失控有帽**：日配额、并发、`maxToolRounds≤4`、单次 120s、走 gift 计费。
6. **能短多轮**：「折扣查完再问 TPM」同会话带上 userId。

### 缺点

1. **慢、贵**：每一轮都是一次完整 `chat/completions`；点页面查同一条会更快更便宜。
2. **路由仍靠模型**：该调哪个 Tool、要不要展开系列折，模型决定；漏一轮则答案可能不全。入参白名单能挡乱扫，挡不住「查了但没查全」。
3. **表述仍可能说错**：数是对的，人话可能把折扣、倍率、刊例搅在一起。
4. **能力天花板 = Tool 清单**：没做过的问法要加 Tool、改 KB、发版；不是「什么都能问」。
5. **正式开了 SQL GATE**：灵活补洞，也把「模型写 SELECT」重新引入（仍有白名单 / LIMIT / 超时）。
6. **轻量 RAG 会漏**：KB 是关键词 / BM25，问法一偏可能没注入对的说明书。
7. **复杂问题 4 轮不够**：只能串行，可能截断。
8. **只读副本延迟**：刚在 Admin 改的折扣，助手可能查到旧值。
9. **没有质量闭环**：没有黄金问答集、正确率、幻觉率。

### 对照

| | 这套做法 | 代价 |
|--|--|--|
| vs 传统 RAG | 能查活数据 | 多轮 LLM，更慢更贵 |
| vs Multi-Agent | 实现简单、好审计 | 复杂题串行、易漏 Tool |
| vs 固定问答 / 页面 | 自然语言、少跳页 | 正确性依赖路由 + 表述 |
| vs 模型自由 SQL | 安全、结果稳 | 覆盖面受 Tool 限制 |
| vs 运营自己写 SQL | 权限和脱敏内置 | 灵活度不如人手 |

## 15. 适用边界

**适合：** 问法多样、但都能落到已有查询；要中文答案 + 证据；绝对不能改数、不能出 Key。

**不适合：** 要毫秒级查询、要开放分析、要多部门视角汇总、要自动改配置。那些该继续用页面，或另做 Multi-Agent / 报表，而不是把这只助手撑大。

一句话：用 **可控性换灵活性**——对内部只读数据助手是对的；短板是慢、贵、覆盖靠 Tool、对错仍有一截握在模型的「选工具 / 写人话」上。

---

## 16. 产品经理要做到哪些

设计这类助手，PM 的工作不是「写一句 prompt」，而是把 **菜单、边界、权限、信任、验收** 定死。研发实现 Loop；菜单上有什么菜、什么不能问，是产品的活。

### 16.1 先拍板的 8 件事（不拍就不要开工）

| # | 你要定什么 | 本助手的定案（作模板） |
|---|----------------|------------------------|
| 1 | **给谁用、替代哪段劳动** | Admin 运营；替代「跳多个页面 / 找研发查库」 |
| 2 | **能问什么 / 绝不能做什么** | 只读业务问答；禁闲聊、禁改数、禁出 Key、禁外网搜索 |
| 3 | **走决策树选哪一档** | 跨多数据源、不需要多专家 → 单 Agent + 白名单 Tool |
| 4 | **P0 菜单（Tool 清单）** | 每条运营高频问法对应一个（或一组）Tool，分期 P0/P1/P2 |
| 5 | **权限是否多开一扇门** | 开门用 `ops.agent.use`；查折扣仍等同 `users.list.view` |
| 6 | **答案怎样才算可信** | 必须落到 Tool 结果 + 展示 evidence；对不上页面算失败 |
| 7 | **对话形态** | 业务问答，不是 Chat；允许同主题短多轮 |
| 8 | **谁付钱、用多少** | 系统账号 gift；日配额；用量可审计；不算真实收入 |

### 16.2 你必须自己写出来的材料

工程可以帮你落库，但下面这些如果 PM 不写，研发会按「能问就尽量问」做大，后面收不回来。

**1. 一句话 + 非目标**

- 一句话：谁、在哪、问什么、不干什么。
- 非目标清单：不做对客 Chat、不做写操作、不做完整向量 RAG、不做 Multi-Agent……写得越像「砍需求」越好。

**2. 典型问法 → Tool 映射（这是核心）**

至少覆盖 P0 的 10～20 句真人会问的话，写成：

| 运营原话 | 期望点哪些 Tool | 答案里必须出现什么 | 不要出现什么 |
|----------|-----------------|--------------------|--------------|
| 查 foo@x.com 的折扣 | lookup_user → get_user_discount → 必要时 expand | 系数、几折、系列是否展开 | 密钥、别的用户 |

没有这张表，就没有菜单，模型只能瞎点。

**3. 知识库大纲（给人看的说明书）**

模型只能按你写的说明书找数。PM 要定：

- 能碰哪些表 / 字段（大白话语义，不是 DDL）
- 名词对照：折扣 vs 倍率 vs 刊例 vs 几折
- 标准问法
- 安全红线：禁止表、禁止「给我 Key」

真源可以是 Markdown；谁改 KB 谁发版，也要定。

**4. 权限矩阵**

- 谁能打开助手
- 每个 Tool 复用哪条**已有** Admin 权限（原则：多一个问法，不多开一扇门）
- 无细权时：直接说没权限，还是假装查不到

**5. 信任与失败体验**

- 证据区要不要默认展开
- 副本可能有延迟，要不要脚注
- 拒绝闲聊、拒绝要 Key、超时、RO 未就绪、4 轮用尽：各说哪句人话
- 长表（价目）是否禁止模型手写，改由服务端拼表

**6. 黄金验收集**

上线前 PM 签字的不是「能聊」，而是：

- 和页面数据一致的 8～15 个真实问题
- 安全反例：要 Key、闲聊、越权、改数
- 无权限账号问折扣 → 必须 forbidden
- 系列折必须展开（否则产品语义错）

**7. 分期与开关**

- P0 必须有哪些 Tool，缺了助手就不要开入口
- SQL 兜底默不默认开（本助手正式开了，这是产品风险决策）
- 未配只读库 → 整个助手不可用，还是降级

**8. 成本与审计**

- 日人均几次
- 账单记在哪个系统用户
- 大盘要不要排除这个账号，避免污染 TOP 用户

### 16.3 建议的工作顺序

```
1. 访谈：运营现在查一条折扣要点几下、找谁
2. 收集 30 句真实问法，聚类成「菜单类目」
3. 用决策树选架构（多数内部查数助手 = 本档）
4. 写非目标 + 权限 + 安全红线（先砍，再做）
5. 把问法写成 Tool 清单 P0/P1，和研发对「有没有现成查询可封装」
6. 写 KB 大纲和黄金问题
7. 定入口 UX（浮层 vs 独立页）、证据、拒绝文案
8. 定配额 / 计费 / 发版开关
9. 跟验收：对页面、对安全反例，不对「答得像人」
```

### 16.4 可以交给研发、但你要会审的

| 项 | 你要问的一句 |
|----|----------------|
| Agent Loop 几轮 | 一轮不够的组合问，4 轮能不能跑完 |
| Function Calling 不稳怎么办 | 有没有 JSON 降级，答案会不会把 raw JSON 直接展示 |
| 只读账号 | 没配 RO 能不能上线（本助手：不能，503） |
| 模型选错 Tool | 入参有没有白名单；漏调展开怎么办 |
| 知识库检索 | 问法换种说法还能命中吗 |
| 评测 | 有没有把黄金集做成可重复跑的探针 |

### 16.5 你不必亲自做的

- Orchestrator 代码、Flyway、RO 角色 SQL
- native tools vs JSON 协议探针
- 具体 JDBC 与脱敏正则

这些是实现细节；产品要的是：**菜单、红线、和页面一致、失败时人话清楚。**

### 16.6 一份最小设计文档目录（可直接当提纲）

1. 一句话 + 给谁 + 现状痛点  
2. 目标 / 非目标  
3. 选型（决策树结论）  
4. 典型问法 → Tool 映射（P0/P1/P2）  
5. 权限矩阵  
6. 安全红线（Key、写操作、闲聊）  
7. 入口与答案形态（含 evidence、拒绝）  
8. KB 谁维护、注入什么  
9. 计费 / 配额 / 审计  
10. 黄金验收 + 安全反例  
11. 分期与上线开关  

本仓库两份 V4.2 设计稿，就是按这个骨架写完并能发版的例子。PM 最少要能独立完成其中 **2、4、5、6、10**；其余可与研发共写，但结论必须产品签字。
