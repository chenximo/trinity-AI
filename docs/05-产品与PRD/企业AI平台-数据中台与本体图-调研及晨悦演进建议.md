## 一、执行摘要

1. **「平台产品经验」≠「做过后台管理系统」**。运营后台是平台的运营控制面；平台本体是可复用能力底座（API / 数据资产 / 业务对象等）。
2. 一份典型高级 AI 产品 JD（运营飞轮 + 平台经验 + RAG/Agent + 本体/图 prefer + Palantir/Agentforce 加分）的**主靶心**是：  
   **企业知识/对象层 + Agent 能力 + 上线后数据飞轮**，不是纯 API 网关，也不是纯搭 Bot。
3. **晨悦 / LinkAI** 属于「一站式智能体搭建平台」（类型 C），晨悦在**评测中心 / 线上回流**上更贴近 JD 的运营飞轮；二者都**补不齐**完整数据中台 / 本体 / 图。
4. **Trinity** 属于「AI 能力聚合 / API 网关」（类型 A）；写经历应讲整条平台，不要只讲后台。
5. 若晨悦长期靠拢：不要仿整套数据中台；最值得做的是  
   **可被 Agent 执行的轻量本体（对象–关系–动作）+ 数据接地 + 质检飞轮升级**；图按场景加。

| 职责 | 含义 |
|------|------|
| 监控看板与 KPI | 上线后可度量、可运营 |

| 深入业务、规模化采用 | ToB 落地与持续使用，不是演示 Demo |

### 2.2 典型硬要求

| 要求 | 解读 |
|------|------|
| 5 年+ 企业级数据平台/中台、AI 平台、行业数字化；主导 0→1 或 1→N | 要过复杂问题抽象与平台化沉淀，不是页面堆砌 |

### 2.3 加分项揭示的金标

- [Palantir Foundry / AIP](https://www.palantir.com/platforms/aip/)：企业数据 + **Ontology** + Agent

→ 岗位要的「平台」更接近 **企业 AI 决策 / Agent 操作系统**，而非 OpenRouter 式网关，也非单纯 Dify 式搭建器。

## 三、平台类型地图

### 3.1 总览

| 类型 | 一句话 | 主要服务谁 | 交付物 |
|------|--------|------------|--------|
| **数据中台** | 把企业数据变成可复用资产 | 数仓/数据工程、分析师、用数业务 | 表、指标、标签、数据 API |
| **AI 平台 A：能力聚合/网关** | 多家模型 → 统一可调用能力 | 开发者、业务系统、运营/财务 | API Key、统一推理、用量账单 |
| **AI 平台 B：训练/MLOps** | 数据→训练→部署管起来 | 算法、ML 工程 | 实验、模型版本、推理服务 |
| **业务中台** | 交易/会员/订单等共享服务 | 各业务线研发 | 中心化服务与主数据 |
| **C：应用搭建平台** | 工作流/Agent 快速出应用 | 业务运营、应用开发/交付 | Bot / Agent / App |

### 3.2 数据中台：服务谁、含什么

**服务谁**：建设方（数据工程/数仓）、使用方（分析/运营/业务系统）、治理方（数据管理/安全）。

**常见模块**：采集集成 → 开发调度 → 数仓建模 → 指标/标签 → 资产目录与血缘 → 质量治理 → 安全权限 → 数据服务 API →（外围）BI。

**体验感**：工作空间、任务流、表目录、血缘图——不是 Chat。

### 3.3 AI 平台 A（网关）：服务谁、含什么

**服务谁**：开发者、业务系统、内部运营、财务/商务。

**常见模块**：统一 API、模型目录、路由/Fallback、鉴权配额、计量计费、可观测、数据策略、用户控制台、运营后台。

**对标体感**：[OpenRouter](https://openrouter.ai/)（Chat / Models / Key / Usage）。

### 3.4 AI 平台 B（训练）：服务谁、含什么

**服务谁**：算法与 ML 工程。

**常见模块**：数据集/标注、训练任务、实验管理、模型仓库、推理部署、监控评估。

**对标气质**：阿里云 PAI、火山方舟精调、AWS SageMaker。

### 3.5 类型 C（应用搭建）：服务谁、含什么

**服务谁**：搭智能体的产品/运营/交付；业务方使用成品 Agent。

**常见模块**：Agent 管理、意图/工作流、知识库、插件、渠道、（进阶）评测与回流。

**对标**：Dify、扣子、[晨悦](https://chenyueinnokeji.com/)、[LinkAI](https://link-ai.tech/)。

### 3.6 关系示意

```
业务系统 ──调用──► 业务中台（订单/会员…）
    │
    └──产生数据──► 数据中台（集成→治理→指标/API）
                         │
开发者/系统 ──API──► AI平台A（模型网关·计费）  ← Trinity 主叙事
算法同学 ──────────► AI平台B（训练·部署）
业务/交付 ─────────► C 应用搭建（晨悦/LinkAI/Dify）
企业决策 Agent ────► Ontology + 数据接地 + Agent（Palantir AIP 类）
```

## 五、竞品定位对照

### 5.1 一句话定位

| 产品 | 归类 | 一句话 |
|------|------|--------|
| **Trinity** | AI 平台 A | 上游多模型 → 统一 API → Key/计量；运营后台为供给与规则控制面 |
| **晨悦 ChenyueFlow** | C（加强质检） | 零代码 Agent：工作流/知识库/插件 + **评测中心飞轮** |
| **LinkAI** | C + MaaS + SuperAgent | 一站式智能体 + 模型服务 + 超级助理；开源生态强 |
| **OpenRouter** | A | 国际网关标杆 |
| **DataWorks 等** | 数据中台 | 数据全生命周期 |
| **Palantir AIP** | 企业 AI 操作系统 | 本体 + 数据 + Agent |
| **海致 Atlas 等** | 图谱/图计算 + 数据智能 | 国内「图 + 知识」主力之一 |

### 5.2 晨悦能力结构（摘自控制台信息架构）

| 分区 | 模块 | 能力含义 |
|------|------|----------|
| 工作台 | Agent 管理、对话 | 建/管/试 |
| 智能编排 | 意图中心、工作流 | 意图路由 + 多步编排 |
| 能力中心 | 能力库、知识库、插件 | RAG + Tool |
| **质检** | 质量报告、评测中心、记忆 | **运营飞轮（最贴高级 AI 运营岗）** |
| 接入 | 渠道、定时触发 | 投放与触发 |

评测中心典型闭环：`入集 → 补齐冻结 → 运行 → 标注完结`（含线上回流、评测集、标注站、Bad Case、意图影子等）。

### 5.3 与「高级 AI 产品岗」匹配度（相对）

| 维度 | 晨悦 | LinkAI | Trinity | Palantir 类 |
|------|------|--------|---------|-------------|
| 搭 Agent / 工作流 / 知识库 | ✅ | ✅ | 非主业 | ✅（对象上） |
| 线上回流 / 标注 / 评测 | ✅ 强 | 视产品线 | 弱 | 企业级治理 |
| 统一模型 API 网关 | 配置级 | 有 MaaS | ✅ 主业 | 非主叙事 |
| 数据中台 / 本体 / 图 | ❌ | ❌ | ❌ | ✅ / 核心 |

### 5.4 Trinity 后台算不算「平台经验」？

| 写法 | 判断 |
|------|------|
| 只写「运营后台管理系统 0→1」 | **偏弱**——像配置中心/CRUD |
| 写「AI API 聚合平台 0→1/1→N，后台为供给与运营控制面」 | **可算 AI 平台 A** |
| 单独等同「数据中台」 | **不算** |

手册中的三层分工（供对照）：运营后台 → 平台侧 API → 用户侧；工程见 `trinity-ai-admin` / gateway / 用户面。

## 六、数据中台 · 本体 · 图

### 6.1 分别是什么

| 概念 | 真正在管什么 | 常见误解 |
|------|--------------|----------|
| **数据中台** | 多源接入、建模、指标口径、血缘、质量、数据服务 | 「有几张报表」≠ 中台 |
| **本体 Ontology** | 企业对象与关系的形式化模型 + 约束/规则；系统与 AI 共用语义 | Prompt 人设、文档知识库 ≠ 本体 |
| **图 Graph** | 多跳关系存储与查询（人–企–合同–风险等） | 任意「关系可视化」≠ 图平台 |

### 6.2 晨悦能否「补齐」？

**结论：现有能力补不齐；最多沾「知识与记忆」。**

| 晨悦模块 | 易被误读为 | 实际差距 |
|----------|------------|----------|
| 知识库 | 数据中台 / 本体 | 文档检索资产，不是主数据与指标 |
| 记忆 | 图 / 实体关系 | 会话记忆，不是企业图谱 |
| 插件连 API | 数据服务 | 点状调用，无中台级治理 |
| 意图 / 能力库 | 本体 | 对话技能目录，不是领域对象模型 |

简历上也不宜宣称「做过晨悦 = 有本体/图经验」。

## 八、晨悦长期演进建议

### 8.1 战略定位

| 方向 | 建议 |
|------|------|
| 全量数据中台 | **不主做**（与 DataWorks 死磕，客户重叠与投入不匹配） |
| 通用建图平台 | **不主做**（客户要办事，不是再买建图工具） |
| **可运行轻量本体 + 数据接地 + 质检飞轮** | **主靠拢** |
| 现有编排 / 知识库 / 评测 | **保留并升级为闭环入口** |

**目标表述**：从「搭对话 Agent」演进为「业务对象上的可执行智能体平台」。

### 8.2 最值得借鉴的四块（优先级）

| 优先级 | 能力 | 借鉴来源 | 最小集 |
|--------|------|----------|--------|
| P0 | **业务对象模型（轻量本体）** | Palantir Ontology / Agentforce Object | 对象类型、属性、唯一键、状态、关系、**Action（含权限/审计）** |
| P1 | **数据接地** | 元枢「接地」；Palantir object backed by data | 属性↔表/API/插件；实例可查、关键动作可写 |
| P2 | **质检飞轮接到对象/动作** | 晨悦评测中心自研优势 | Bad Case 标到对象/Action；回流改模型/映射/规则/Prompt |
| P3 | **图（按需）** | 海致 / 华为 KG | 仅股权、供应链、设备拓扑等多跳刚需场景 |

### 8.3 演进路线（建议）

```
现在：Agent + 工作流 + 知识库 + 插件 + 评测回流
  ↓ Phase 1（约 3–6 月）
对象模型 MVP + 2～3 个垂直对象（如：用户阶段档案、工单、SKU）
Action 替代部分裸插件；评测可标「对象/动作」
  ↓ Phase 2
多源接地（API/表）；权限挂对象；工作流编排「对象动作」
  ↓ Phase 3（有明确客户再上）
关系/图查询、规则推理；对接外部数据平台（不自建完整中台）
```

每个 Phase 应用**真实场景**验收（如母婴顾问、智能客服），避免空转建模。

### 8.4 现有模块改造抓手

| 模块 | 改造方向 |
|------|----------|
| 能力中心 | 增加「业务对象 / 模型」；知识库降为对象的证据源之一 |
| 工作流 | 节点：查询/更新对象、调用 Action |
| 插件 | 降级为 Action 的实现适配器 |
| 评测中心 | Bad Case 结构：意图 / 检索 / **对象** / **动作** / 话术 |
| 记忆 | 绑定会话中的**对象实例**，不只聊天摘要 |
| 渠道 | 可不变；差别在是否操作企业对象 |

### 8.5 明确不做

- 全链路 ETL、指标平台、血缘大屏作为主产品  
- 一上来对标海致 Atlas 全量建图 Studio  
- 把「接了几个数据库」包装成「有本体」  
- 为堆 JD 词汇而加空菜单——本体/图必须能被 Agent **执行并被评测**

### 8.6 成功标准

- Agent 操作的是「工单 / 订单 / 档案」，而不只是「搜到一段文档」  
- 错案能回流到**对象定义、映射、Action、Prompt**  
- 在 1～2 个垂直场景形成可复制的对象模板
