## 0. 结论（一句话）

Trinity **已具备** FinAPI 的**入口与计量底座**（统一网关、刊例扣费、工作区/Key 用量、子区消费限额），**尚未**做成文中那套完整的「企业经营 AI 成本」治理体系。本文把缺口收成分期 TODO，供路线图排期。

**命名纪律**：对内称 **「AI 调用成本治理」**；不擅自使用竞品「FinAPI」作为产品名，除非品牌侧另行拍板。

## 1. 现状 vs 目标（对照表）

| FinAPI 管什么 | Trinity 今天 | 规划态度 |
|---------------|--------------|----------|
| 统一入口 | ✅ 统一 OpenAI 兼容网关 | 保持；强化「必经网关」客户侧落地指引 |
| 成本归属 | 🟡 工作区 / 子工作区 / API Key | **加码**：标签、应用/Agent、可选组织映射 |
| 预算执行 | 🟡 钱包余额 + 子区消费限额 + Key 限流/冻结 | **加码**：预警、多维规则、类熔断策略 |
| 账单可信 | 🟡 用量与扣费同源；平台侧上游对账运营 | **加码**：客户侧异常识别与对账导出 |
| 成本 ↔ 价值 / ROI | 🟡 调度 / Auto / 缓存等工程手段 | **谨慎**：先做「可解释成本优化」，ROI 业务价值后置 |
| 不管：训练 / Agent 逻辑 / 全套安全合规 | ✅ 边界清晰 | 继续划清，不把成本治理扩成「全部 AI 治理」 |

## 3. 明确不做（本期边界）

| 不做 | 原因 |
|------|------|
| 训练 / 微调大模型 | 非网关成本治理范围 |
| 代替客户设计 Agent 业务逻辑 | Agent 平台职责 |
| 用成本治理包办内容安全 / 行业合规 | 另有安全与合规体系 |
| 「一切以最低单价为目标」 | 与产品原则冲突 |
| 用量档 / 刊例阶梯自动改扣费冒充「预算治理」 | 达档洽谈 ≠ 实时预算熔断（见定价方案原则） |
| 未拍板前对外宣称「FinAPI 已具备」 | 能力未齐，易翻车 |

---

## 4. 建议排期原则

1. **先 Phase 0 + Phase 1**：低成本把「能讲清楚、能按部门/项目看见与限额」做实——这是客户感知最接近 FinAPI 的一层。  
2. **Phase 2 与计费/风控同排**：预算熔断会动热路径，需网关 + 控制台 + 通知一起设计。  
3. **Phase 4 不抢跑 ROI 故事**：有 G-OPT-01/02 再谈「优化」；ROI 等有标杆客户再写 Case。  
4. **与现有真源对齐后再立项**：工作区配额、计量、鉴权限流 roadmap；改字段须过计量口径三处对齐。
